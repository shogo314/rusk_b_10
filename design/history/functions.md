## 関数本体と戻り値

通常の関数本体は処理を書くブロックとし、値を返すときは `return` を明示する。ブロック式の末尾の値を、関数の戻り値として暗黙に返すことはしない。

```rusk
fn square(x: Int) -> Int {
    return x * x;
}
```

短い関数には、式をそのまま戻り値とする式形式も用意する。構文の候補は `fn square(x: Int) -> Int => x * x;` とし、具体的な表記は未確定。無名関数の式形式と揃える方向で考える。

戻り値の型を省略した通常の関数は、既定の方針どおり `Unit` を返す。式形式での戻り値の型推論は未決定。

`Unit` 以外を返す関数では、値を返さず本体の末尾に到達できる場合をコンパイルエラーとする。既定値を暗黙に返すことはしない。

無限ループや必ず異常終了する処理など、通常の制御で戻らない経路も扱えるようにする。判定は構文や制御フローから判断できる範囲を基本とし、任意の条件式が常に真であることなどの高度な証明は要求しない。戻らない関数には専用の型（仮名 `Never`）を用意する。到達不能の判定規則などの詳細は未決定。

## 内側の関数と外部変数

関数の中に名前付きの関数を定義でき、再帰呼び出しもできるようにする。内側の関数が参照する外側の変数は、デフォルトでそのオブジェクトを共有して捕捉する。

捕捉したオブジェクトの中身を更新すると、外側からも更新が見える。一方、内側の関数で捕捉した名前を `:=` で結び直しても、外側の変数が指す先は変わらない。読むだけの制限は捕捉しても維持する。

捕捉したオブジェクトは必要な間生存し、外側の関数を抜けた後も使える設計を重視する。これは動的な関数値を導入するものではなく、呼び出すコードを静的に決める方針は維持する。

捕捉は関数の定義時に行い、その時点で外側の変数が指すオブジェクトをコピーせず共有する。外側で `x = ...` と中身を更新すれば見えるが、`x := ...` と結び直しても捕捉先は変わらない。無名関数も、作成時点で同じルールにより捕捉する。配列などの中身のコピーは行わず、共有を保持する管理方式は別途設計する。

同じスコープの型名・関数名は定義順によらず参照でき、関数の相互再帰も許す。前方宣言は要求しない。再帰呼び出しと捕捉した名前の結び直しの関係などは未決定。

必要な捕捉先・捕捉環境がまだ用意されていない時点での呼び出しはエラーにする。関数名が見えることと、その関数を呼び出せる状態であることは区別する。ループ内などで関数の定義を繰り返し実行する場合は、その都度のオブジェクトを捕捉する環境が必要となる。コードの静的な特殊化とは別に、環境は実行時に用意される。

捕捉環境を必要としない関数は定義前から呼び出せる。捕捉環境が必要な関数は、その環境が用意された後でなければ呼び出せない。このエラーの検出方式、間接的な呼び出しでの検査、相互再帰する関数の捕捉環境の準備などの詳細は未決定。

## 取得関数と読み取り権限

更新しない取得関数を、更新可能な入力と読むだけの入力の両方に使え、入力から共有する戻り値にも適切な権限を引き継げることを設計目標とする。読むだけの入力から、更新可能な共有を得ることは許さない。

この目標は、更新可能な引数を要求する関数へ読むだけの値を無条件に渡せるという意味ではない。関数の定義で更新しないことや権限の対応をどう表すかは別途設計する。

通常の型引数で表現するか、権限用の引数を設けるか、別定義や自動生成を使うかなどの実現方法と具体的な構文は未決定。

## 名前付き引数

関数呼び出しで名前付き引数を使えるようにする。ヒープやソートで、キー関数と比較関数を明確に指定する用途などを想定する。

```rusk
sort(a, key = _.score);
sort(a, comp = _ < _);
let q := MinHeap<State>(key = _.distance);
```

これらは呼び出し形の例であり、ソートやヒープの最終的なシグネチャを確定するものではない。

オーバーロードなどの複雑化を避けるため、当面は位置引数と名前付き専用引数を分ける。位置引数は位置で渡し、名前付き専用引数は必ず名前を付けて渡す。どちらでも渡せる引数は設けない。定義での区別の表記は未決定。

呼び出しでは位置引数を先、名前付き引数を後に書く。名前付き引数同士の順序は自由とし、重複指定や未知の引数名はエラーとする。引数の式は、定義順ではなく呼び出しに書いた左から右の順で評価して保持し、共有を保って対応する引数に渡す。

名前付き専用であることと既定値の有無は区別する。

名前付き引数の名前もオーバーロード候補を絞る条件に使う。指定された名前を受け取れない定義や、必須引数が不足する定義は候補から外す。残った候補は型・具体性の既定の規則で選び、一つに決まらなければコンパイルエラーにする。既定値のある候補が複数残っても、宣言順では選ばない。

この規則により、`sort(a, key = f)` と `sort(a, comp = g)` のように名前付き専用引数の異なる定義を同名で用意できる。関数の重複定義の判定でも位置引数と名前付き専用引数の区別、および名前付き専用引数の名前を考慮する。ジェネリックな候補などの厳密な判定は今後詰める。

## 引数の既定値

名前付き専用引数には既定値を指定できる。既定値は、その引数が省略された呼び出しごとに評価する。たとえば空配列リテラルを既定値にした場合は毎回新しい配列を作り、定義時に一度だけ作った配列を暗黙に使い回さない。

呼び出しに指定された引数を記述順に評価した後、省略された引数の既定値を定義順に評価する。既定値の式から、定義上それより前の引数を参照できる。参照や共有を返す式の場合は既存の共有ルールに従い、既定値の評価自体が常に独立した値を保証するものではない。

既定値の具体的な宣言構文、外側の変数の捕捉との関係、位置引数にも既定値を認めるかなどは未決定。

## オーバーロードの基本方針

関数名は、探索の起点から外側へたどり、その名前の関数を定義している最も内側のスコープを選ぶ。そのスコープの同名関数だけを候補集合とし、外側のスコープの候補は混ぜない。引数に適用できる候補がなくても、外側へ探索し直すことはしない。その集合の中で引数名・型・具体性などの規則に従って選び、適用不能や曖昧さはコンパイルエラーにする。

同じ引数の型・個数を持ち、位置引数・名前付き専用引数の区別と名前付き専用引数の名前も同じ関数の重複定義はエラーとし、読み込み順による上書きは行わない。標準ライブラリに対しても同じ規則を適用する。重複した両方の定義位置を診断に表示する。ジェネリックな宣言同士の同一性など、詳細な判定規則は今後詰める。

同名の関数は、引数の個数と型で選ぶ。候補を選ぶための暗黙の型変換は行わない。

具体的な型を指定した定義と、ジェネリックな定義の両方が適用できる場合は、具体的な定義を優先する。優先する候補が一つに決まらなければコンパイルエラーにする。

```rusk
fn f(x: Int) { ... }
fn f<T>(x: T) { ... }
f(10); // Int 版を選ぶ
```

複数のジェネリックな定義の具体性の比較など、候補間の厳密な優先順位は未決定。戻り値から型引数を推論することと、戻り値の型だけでオーバーロードを選ぶことは区別する。後者を許すかは保留する。

## β02で実装する具体化の範囲

β02では型と名前付き関数をトップレベルに限定し、具体化した本体でも同じグローバルの型・関数群から名前を解決する。引数から型引数を推論し、明示指定は `f::<T>(...)` とする。具体型の完全一致を優先し、ジェネリックな候補が複数適用できれば曖昧として拒否する。型引数を明示した呼び出しはジェネリックな定義を対象とする。

これは現段階の実装範囲であり、ローカル型・捕捉環境・mixin・トレイトを含む最終的な名前解決を決定するものではない。型引数を持つ構造体の構築式には `Pair::<Int, Str> { ... }` を使い、型注釈は `Pair<Int, Str>` とする。

## ジェネリック処理の名前解決の候補

状態：再検討中。以下は一度支持された mixin 方式の候補であり、最終採用は未決定。暗黙の静的引数やトレイト方式と比較する。通常の名前を定義場所で解決することは共通の出発点とする。

通常の名前はジェネリック関数を定義した場所を基準に解決する。明示的に指定した識別子だけ、具体化する呼び出し側のスコープを起点として解決できるようにする。Nim の `mixin` を参考にするが、正式な宣言構文は未決定。

```rusk
fn twice<T>(x: T) -> T {
    mixin __add__; // 仮の記法：この名前は具体化側で解決
    return x + x;
}
```

具体化側での解決にも、最も内側の同名関数の定義スコープだけを候補にする規則を適用する。Nim の open な名前のように定義側と具体化側の候補を自動的に合併することは前提にしない。オーバーロード可能な名前をすべて暗黙に具体化側へ開くこともしない。

この候補では、型の定義元から関数を追加探索しない。ローカル型の値がその定義スコープの外へ出た後で具体化され、必要な関数が見つからない場合はコンパイルエラーでよいとする。

この指定を明示的な型引数のない通常の関数でも使えるようにする案がある。ジェネリック関数を何段も経由する場合の具体化側の起点や候補の引き継ぎ、捕捉環境の受け渡しなどは未決定。必要な捕捉環境が未準備なら呼び出せない既定の規則は維持する。

## 名前解決の別案と初期実装の提案

以下はいずれも比較・実装範囲の候補であり、採用済みの仕様ではない。

- 必要な演算を暗黙の静的引数として宣言・受け渡しする方式。要求を関数の宣言に表し、必要なら明示指定する。
- `T: Addable` のようなトレイト制約と、型への実装の対応付けを用いる方式。呼び出し場所の同名関数に依存しないが、制約・実装の記述が増える。
- 初期実装では型・名前付き関数をグローバルに限定し、グローバルの候補集合で解決する方式。ローカル型や内側の名前付き関数の検討を延期し、先に実装と実例を増やす。無名関数の捕捉は残す提案がある。

グローバル限定は初期実装の範囲の提案であり、合意済みの内側の関数・捕捉やスコープの目標を削除する決定ではない。ローカル型の持ち出し、無名構造体、名前付き関数の戻り値推論も検討案であり未確定。

## ジェネリック関数に必要な操作

これまでの基本方針は、型に必要な操作を表す制約の記述を必須とせず、具体化時に必要な操作が使えるか検査すること。ただしトレイト方式の検討に伴い、この必須性は再検討対象とする。

```rusk
fn twice<T>(x: T) -> T {
    return x + x;
}
```

この例では、呼び出しで決まった型について加算と戻り値の型などを検査する。エラーには、失敗した操作だけでなく、どの呼び出しからどの型で具体化した結果かも示す。

明示的な制約は必要に応じて将来検討する。具体化の失敗をオーバーロード候補の除外に使うか、選ばれた関数のエラーにするかなどの詳細は未決定。

## 関数を渡す仕組み

関数を渡す仕組みは、呼び出すコードがコンパイル時に決まり、受け取る側をジェネリックに特殊化する方式を基本とする。動的な関数値や型消去による呼び出しは、当面設けない。

外部の変数を参照する無名関数は使えるようにする。実行するコードが静的に決まることと、参照する環境の値が実行時に決まることは区別する。捕捉は上記の名前付き関数と同じ方針とし、環境の具体的な表現などは今後詰める。

関数を通常の引数の形で渡して静的に特殊化する構文は候補とするが、最終的に明示的なジェネリクスの構文で渡す形でもよい。表記よりも、静的に呼び出すコードを決められることを基本方針とする。異なる関数を実行時に選んで同じ変数へ格納する機能は、当面の基本機能に含めない。

この方針は動的な呼び出しのコストを避け、インライン化などの最適化をしやすくすることを意図する。実際の性能は実装時に確認する。

## オーバーロード集合の静的な受け渡し

関数を渡す必要がある場面では、単一の関数だけでなくオーバーロード候補集合を静的に渡し、受け取った側で呼び出す際の引数型に応じて選ぶ方式を有力案とする。D のテンプレート alias 引数による受け渡しが参考になる。

渡す場所の名前探索で候補集合を確定し、使用時にその集合から既定のオーバーロード規則で選ぶ方向で考える。一つに決まらなければコンパイルエラーにする。実行時に呼び出し先を選ぶ動的な関数値を導入するものではない。

受け渡す構文、候補集合の同一性、候補ごとの捕捉環境の保持・準備方法などは未決定。この方式の採用は、ジェネリック関数内の演算をすべて明示的な引数として渡すことや、型の定義元からの追加探索を採用することまで決めるものではない。

## コンパイル時の値とジェネリクスの構文案

型や関数だけでなく、整数などのコンパイル時に確定する値に応じた特殊化も検討する。関数に応じた特殊化とは別に、対応範囲を決める必要がある。

用途の一つは、異なる型の要素を持つタプルからの要素取得とする。`t[0]` を `get(t, 0)` のように扱い、静的な添字に応じて戻り値の型を決める構文が候補にある。ただし、最終的には `get::<0>(t)` のようにジェネリクスを明示する書き方でもよい。これらの構文は未確定。

実行時にしか分からない添字で異種タプルを取り出す方法は未決定。静的な値を要求する引数の宣言方法、定数式の範囲、推論方法、明示的なジェネリクスとの関係は、具体的な設計時にまとめて検討する。

## 無名関数の構文案

無名関数を簡潔に書けることを重視する。当面は、短い式に Scala 型のプレースホルダー `_` を使い、引数の再利用や複雑な式には `x => ...` のように引数名を明示する構文を併用する案を検討する。

この案では `_ + 1` は `x => x + 1`、`_ < _` は `(x, y) => x < y` に相当し、各 `_` を別の引数として扱う。同じ引数を繰り返し使う場合は `x => x + x` のように書く。構文の採用は未確定で、プレースホルダーが属する式の範囲、入れ子、型推論などの規則は未決定。

利用例として、探索結果が存在する場合だけ 1-indexed に変換し、不在なら `-1` を返す `a.find(x).map(_ + 1) ?? -1` のような記述を想定する。列と Option の `map` の基本方針は collections.md に記録する。`??`・`?!` の具体的な構文や詳細仕様は引き続き検討中。
