## 今回の目標

変更・副作用・共有・脱出の情報を中間表現に明示し、解析結果から安全な最適化を行う。言語機能と標準APIはβ06を引き継ぐ。詳しい要件はリポジトリの[design/beta07.md](https://github.com/shogo314/rusk_b_07/blob/main/design/beta07.md)にまとめる。

1. 引数や値への読み取り・中身の更新・コンテナの構造変更・共有先の保持や返却・コールバック呼び出しの効果を表す。
2. HIRで具体的な関数の効果を求め、LIRにも保持・反映する。externや解析できない処理は保守的に扱う。
3. 値が戻り値・コンテナ・フィールド・enum・捕捉などを通じて外へ保持されるかを解析する。
4. 寿命を保証できる一時参照の借用、非脱出スカラーの値保持、不要なコピーや検査の削減へ利用する。
5. 引数・ローカル変数にreadonly/mutable・fixed/rebindable、引数にnoescape/escapeを任意で指定できるようにする。本体・別名・呼び出し・コールバック経由の利用を検査し、別の共有先を含めた不変性は別途解析する。
6. 通常版・最適化無効版の比較、共有と寿命のテスト、サニタイザー、公開問題、ベンチマークで検証する。

## 注釈と自動解析の役割

β07では、次の3組を使う。各性質は独立で、省略時の既定値も明示できる。

| 性質 | 指定 | 省略時 | 対象 |
|---|---|---|---|
| 中身の変更 | `readonly` / `mutable` | `mutable` | 引数・ローカル変数 |
| 名前の結び直し | `fixed` / `rebindable` | `rebindable` | 引数・ローカル変数 |
| 共有の持ち出し | `noescape` / `escape` | `escape` | 引数 |

導入予定の構文例：

```text
readonly fixed let view := values;
mutable rebindable let working := values;
fn sum(readonly noescape a: Vec<Int>) -> Int { ... }
```

readonlyはその名前やそこから得た別名を通じた変更を禁止し、fixedは名前の初期化後の結び直しを禁止する。例えばmutable fixedなら、中身の`=`による更新は可能である。noescapeは引数やその内部への共有を呼び出し終了後まで外へ残さない契約とする。escapeは脱出を許可し、実際に脱出することを要求するものではない。ローカル変数のnoescape/escapeや、フィールド・型全体への一般化は今回の範囲外とする。

これらは意図した契約を実装が破っていないか検査するための任意の注釈である。注釈がなくても本体と呼び出し先を解析し、証明できた読み取り専用・非脱出などの性質をHIR/LIRへ記録する。mutable・rebindable・escapeが明示されていても同じであり、同じ性質が証明できれば同じ最適化へ使う。既存コードに注釈を必須としない。

宣言した契約・解析で証明した性質・externなどの信頼する契約は区別する。解析不能な場合は安全側に扱い、変更しないことと副作用全体がないことを混同しない。readonlyでも別の共有先からの更新は見え、noescapeでもmutableなら更新できる。fixed/rebindable・readonly/mutable・noescape/escapeの初期実装は完了した。

## 戻り値とコールバックの解析

戻り値が引数自身やその内部の要素を共有するのか、独立した新しい値・コピーなのかを解析情報として記録する。共有関係を表す戻り値注釈を利用者に要求するものではない。例えば`return a[0];`の結果はaの要素を共有し、`return copy(a[0]);`は独立した値になる。呼び出し側へ関係を伝え、別名・readonly・寿命の解析に利用する。分岐の候補と不明な由来も保守的に扱う。

コールバックは、処理を任せるために渡す関数値である。即時呼び出し、別の関数への受け渡し、格納・捕捉・遅延イテレータでの保持を区別し、捕捉値への変更や共有、入出力、失敗し得る処理、結果を通じた脱出を解析する。map・filterは遅延走査のためコールバックを保持する。その場で呼ぶだけでも、結果として捕捉値への共有を返し得るので、保存の有無だけでnoescapeとは判断しない。

## 契約違反の診断

readonly・fixed・noescapeの違反箇所と制約の宣言箇所を示し、別名・要素・フィールド・呼び出し・捕捉を経由した違反では、その由来と経路も説明する。解析できず安全を証明できない場合と、明確な違反を区別する。診断の位置・理由・経路をテストし、HIR/LIRの出力でも解析した関係と根拠を確認できるようにする。

これらもβ07の完成条件に含める。fixed・readonly・noescapeの基本診断と、noescapeの別名・射影・呼び出し結果の経路表示は実装済みである。readonlyは結び直し・分岐・既知のヒープ格納・捕捉・通常の関数の返却と内部の変更箇所まで追跡し、不明な部分を明示する。noescapeも通常の呼び出し先の仮引数・局所別名・返却・外への保持操作まで追跡し、内部経路を復元できない理由を示す。

### β08の設計方針：ライブラリの専用処理を減らす

externを含む通常のライブラリ定義へ実装を置くことを優先する。本体をRuskで書くかC++のexternで書くかは、機能・解析可能性・性能を見て選ぶ。トランスパイラにライブラリの関数名・型名ごとの実装や文字列置換を追加し続ける構造を減らす。

現在の主な対象は、`src/compiler/higher_order.rs`が名前を見てC++本体を生成するmap/filter/fold等、`src/compiler/containers.rs`のコンテナ操作、`src/compiler.rs`がVec用宣言の型名・関数名を文字列置換する具体化である。バックエンドが標準関数の名前から直接式を生成する最適化も棚卸しし、ライブラリ宣言と汎用的な情報で扱える範囲を検討する。

先に、必要なジェネリックexternの宣言・具体化、型とC++表現の対応、静的コールバックの呼び出し、効果・共有・保持の情報をどこで表すかを設計する。現在のextern関数構文には型引数の宣言がなく、ライブラリファイルへコードを移すだけでは専用処理を解消できない。

目安は、新しいライブラリ関数や外部ジェネリック型を追加するとき、その名前の分岐をコンパイラへ追加せずに済むこととする。名前解決・型検査・具体化の共通の仕組みを利用者定義のexternにも使えるようにし、組み込みだけが持つ信頼契約の境界は維持する。共有・コピー・寿命の意味は、引き続き型検査・IR・生成処理で保証する。

### 初期解析で実装したこと

- 引数ごとの読み取り・更新・構造変更・脱出・外部保持、入出力・外部状態の更新・失敗・非停止の可能性を区別する。各効果は`No`・`May`・`Unknown`で表す。Mayは起こり得るという上限であり、必ず起きるという意味ではない。
- 戻り値が引数自身・配列や文字列の要素・フィールド・enumのpayloadを共有する関係と、戻す集合値の内部に引数への共有を保持する関係を表す。呼び出し側へ関係を代入して伝播する。捕捉環境もIR上のフィールドとして同じ処理を通る。
- LIRの到達可能な制御フローで分岐・ループの状態を結合し、関数間は再帰・相互再帰を含めて固定点まで解析する。CFGの循環と呼び出しの循環は、非停止の可能性として保守的に扱う。
- 情報の出所を`Unanalyzed`・`Inferred`・`Opaque`・`NativeContract`で区別する。引数数・戻り値の参照先・脱出との矛盾・解析上限をHIR/LIRで検証する。

例えば`fn identity(x: Int) -> Int { return x; }`では、更新しないが引数自身への共有を返すと分かる。`fn value(x: Int) -> Int { x := 7; return x; }`では、引数名の結び直しと共有オブジェクトの更新を区別し、引数への共有を返さないと分かる。

`rusk compile main.rusk --emit hir -o main.hir`または`--emit lir`で、各関数の`effects`を確認できる。戻り値の`result_path`は結果の内部の位置、`parameter`は0始まりの引数番号、`parameter_path`は引数の内部の位置を表す。`fresh`は独立した新規オブジェクトを返す可能性であって、一意所有の証明ではない。最適化の有無で解析情報は変えない。

### 現段階の保守的な扱い

組み込みランタイムの基本操作には、宣言の`effects`プロパティで明示した効果契約を登録する。`lib/core.rusk`の基本演算・コピー・変換・入出力・文字列操作・sumと、`lib/vec.rusk`の長さ・添字取得・真偽変換・空配列構築が対象である。`src/native_effects.rs`でターゲット非依存の情報へ変換し、返却する要素の型と経路も検証する。情報の出所は`NativeContract`であり、Rusk本体を解析した`Inferred`とは区別する。

これは組み込みC++実装との信頼境界であり、ユーザーが書くreadonly等の注釈とは別の内部プロパティである。組み込みランタイム以外での指定は拒否する。関数名やC++コードの見た目から契約を推測しない。未登録の外部実装・コンテナ操作・コールバックを呼ぶネイティブ処理は、引き続きOpaque・Unknownとして保守的に扱う。

フィールドへの格納や変更し得る呼び出しの後では、ヒープの投影を保守的に不明へ広げる。変更前に取得済みの共有は区別する。直接構築した格納先の別名群が関数内に留まると証明できた場合を除き、局所オブジェクトへの格納も脱出の可能性として扱う。直接構築した入れ子の格納先は共有先と到達関係を追跡する。既知の読み取り専用・外部非保持の関数が引数自身や内部を共有して返す場合も追跡する。返却する集約の内部の共有も、元の共有先への到達関係を追跡する。配列操作や返却された格納先の私的性まで精度を高めるには、さらに解析が必要である。引数ごとの更新情報は、その引数を経由したアクセスを表す。異なる引数が互いに共有していないとは仮定せず、更新なしという情報だけで別の共有先からの更新もないとは判断しない。

共有元の候補が64個、経路が16段を超えた場合は不明へ広げる。上限を超えた関係を安全とは扱わない。注釈なしでは利用できる最適化が減り、注釈した契約を証明できない場合には、その理由を診断して拒否する。

## 返却と外部保持を分けた脱出の伝播

`escape`は戻り値を含めて呼び出し終了後へ共有が残る可能性、`retained`は戻り値以外の格納先へ保持される可能性を表す。要素を共有して返すgetterはescapeがMayでも、retainedはNoである。呼び出し元はその戻り値の利用を追跡し、受け取っただけで自身の引数が外へ脱出したとは判定しない。

```rusk
fn first(a: Vec<Int>) -> Int { return a[0]; }
fn detached(a: Vec<Int>) -> Int { return copy(first(a)); }
fn ignored(a: Vec<Int>) { first(a); }
```

firstは要素への共有を返すためaのescapeがMay、detachedとignoredはNoになる。detachedの結果は独立した値である。いずれもaの中身を更新せず、外部の格納先へ共有を保持しないのでwriteとretainedはNoになる。添字が不正なら失敗する可能性は残す。

標準の整数加算・代入・sumなども契約から効果を伝播できる。加算やsumのオーバーフロー、入力・変換・添字の失敗、入出力やブロックする可能性、文字列更新の構造変更を記録する。効果が不明なものを純粋と扱ったり、読み取り専用だから失敗や入出力もないと扱ったりしない。

この段階では脱出伝播の単体テスト、契約の型・形の検証、実際のソースからの効果推論・信頼境界・共有の動作を検査する`tests/effects.rs`を追加し、共通入口の最適化無効版にも含めた。通常295テスト・最適化無効167テスト・fmt・Clippy・MkDocsのstrictビルドで成功した。生成C++は引き続きβ06の172例と一致する。新しい借用・スカラー最適化にはまだ適用していない。

## 関数が返す私的な共有先

私的格納先のグラフへ、既知の関数が引数自身・フィールド・payloadを共有して返す関係を反映した。`returned.aliases`の`parameter_path`で実引数の共有先を投影し、呼び出し結果へ合流する。更新・構造変更・外部保持がNoの引数は、受け渡しだけで公開済みにはしない。ほかの引数は公開し、外部書き込みがNoでない・返却関係が不明・`result_path`が空でない場合は従来の保守的な扱いへ戻す。`fresh`だけで一意性や新しい私的な割り当て位置を作らない。

## 借用した仮引数の閉じた別名

関数シグネチャで借用を選んだInt・Bool・Charの仮引数を、局所的な別名の起点にも使う。選択条件は、関数本体から更新・構造変更・脱出がNo、外部状態の更新もNoと推論できることとする。注釈の省略・制限側・許可側の明示で、推論した性質が同じなら同じ表現を使う。

仮引数をfreshな値と扱うことはない。別名解析の起点をfreshな演算結果・所有する要素・借用した仮引数に分け、仮引数の場合は選択した引数IDだけを起点にする。定義が宣言と共有で閉じた群の局所スロットを、関数冒頭で仮引数への`const Obj<T>&`として結ぶ。元の共有コピーと局所スロットのresetは生成しない。値のスナップショットにはせず、別の共有先による中身の変更は同じオブジェクトから読み取る。

呼び出し元は評価済みの引数のObjを呼び出し終了まで保持するため、これらの別名は分岐・ループ・再帰呼び出しをまたいで有効である。関数冒頭で参照を結ぶこと自体には参照カウントやユーザー定義の初期化処理がなく、ソース上の宣言前に値を読み取ることもない。Boolの評価用コピーは別の新しい値として扱い、条件のスナップショットを共有へ置き換えない。Charも呼び出し元の所有を使い、文字参照の有効期間を延長しない。

群を経由した更新・構造変更・返却による共有・不明な呼び出し、名前の結び直し、集約への保存や捕捉がある場合は従来の所有表現に戻す。仮引数名の結び直しは元の共有先への更新とは異なるため、シグネチャで借用できても局所スロットは所有が必要になる場合がある。通常の関数へ渡す別名は、渡し先でも推論した借用引数となる場合だけ許可する。配列要素を起点とした借用の一基本ブロックという制限は維持する。

回帰テストで分岐・ループをまたぐ別名、通常の関数への転送、再帰、左から右の引数評価と呼び出し元の結び直し、Bool・Char、文字参照の解放を最適化無効版と比較する。局所の結び直し・格納・捕捉で所有が残ること、生成C++で仮引数を参照する別名にresetがないことも検証する。

通常375件・最適化無効221件・ASan/UBSan/LeakSanitizer34件・公開ジャッジ51解答、Formatting・Clippy・MkDocs strictが成功した。公開ジャッジでは有効な検証キャッシュも再利用した。各7回の測定でscalar_callは約11.8→10.0ms、element_callは約31.6→29.3msとなり、共有ポインタコピーはそれぞれ約300万→200万回、約800万→400万回へ減った。確保数は変わらない。callback_foldは約79.8→71.5msとなった。既存11項目と生成C++の対照確認を含め、全結果は[性能記録](beta07-performance.md)に保存した。配列スロットを起点とする借用を通常の関数や制御フローをまたいで行うことは引き続き残る。

## 制御フローをまたぐ要素の別名

Int・Bool・Charの取得済み要素について、所有するObjを一つ残した別名の借用を分岐・ループの前後へ広げる。起点は組み込みVecの添字取得・Iterの次要素取得で、閉じた読み取りと推論した借用引数への受け渡しに限定する。更新・結び直し・返却による共有・格納・捕捉がある群は従来の所有表現に戻す。配列スロットを直接借用する範囲は引き続き一基本ブロック内である。

`src/backend/owned_aliases/flow.rs`で、元の各Objスロットが論理的に生存しているかをCFGの辺ごとに追跡する。各IDの静的な定義は一つとし、ループによる動的な再実行は扱う。定義・入力・解放を元の命令順に調べ、群の入力が生存していること、同じIDを生存中に再定義しないこと、取得元の結果を再取得する際には前の別名がすべて解放済みであることを要求する。合流点の生存集合が経路によって異なる場合は借用を選ばない。同じ状態で戻るループは扱うが、前の反復の別名を残したまま同じ取得スロットを再定義することは許可しない。

各経路で最後の元の別名が解放されるイベントを記録し、そこで所有者のObjをresetする。Returnのcleanupも元のIDの順番で扱い、同じIDの解放でも基本ブロック・命令位置・解放リスト内の位置で区別する。群の全スロットが解放されてから関数を返すことも確認する。所有者は関数冒頭の安定した領域へ置き、別名をそのObjへの`const Obj<T>&`として結ぶ。元の共有コピーと別名のresetを除き、元の配列の置換・破棄・再確保があっても取得済みの要素自身は保持する。値のコピーへは変えず、別の共有先による更新も見える。群の外に同じ要素を共有する値がないとは仮定しない。

これにより、最後の元の所有コピーが消える位置で対象を解放し、文字参照の長さ変更制限や独自の解放処理のタイミングを遅らせない。初期化前に参照を結ぶ処理自体はObjへの参照を作るだけで、中身を読まない。CFGで到達しない命令の別名解放も生成せず、到達可能な経路だけで解放位置を証明する。一基本ブロックで閉じる既存の計画は維持し、新しい解析はその条件を満たさない群へ使う。

追加の解析は関数ごとに100万単位に制限する。CFGの状態配列の確保、命令・入力・解放IDの走査、生存集合のコピー・比較の量を差し引き、上限に達したら残る群では所有表現を維持する。解析が途中で失敗した群へ部分的に借用を適用しない。この上限は効果や注釈の契約検査とは独立で、最適化の選択だけを変える。

単体テストで経路ごとの最終解放、Return cleanup内の位置、合流の不一致、反復をまたぐ別名の残存、解析上限へのフォールバックを検証する。実行テストでは分岐・ループ・continue・早期return、Bool・Char、置換・破棄後の古い要素、文字参照の正常な解放と長さ変更の拒否、走査中の構造変更の診断を最適化無効版と比較する。

通常381件・最適化無効221件・ASan/UBSan/LeakSanitizer35件・公開ジャッジ51解答、Formatting・Clippy・MkDocs strictが成功した。公開ジャッジでは有効な検証キャッシュも再利用した。各7回の測定でfindは約30.3→29.2ms、共有ポインタコピーは約1,400万→1,000万回となった。確保数は変わらない。他の効果測定4ケースと既存11項目は生成C++が比較元と同一だった。既存11項目、追加3項目各11回、生成C++とELF .textの対照確認を含め、全結果は[性能記録](beta07-performance.md)に保存した。配列スロットの直接借用を通常の関数や制御フローへ広げることは引き続き残る。

## readonlyの伝播経路と呼び出し先の操作の診断

既存のAccessPathsによる判定で違反が出た後だけ、`src/readonly/diagnostic/`で診断用の追跡を行う。元の判定が選んだreadonlyの宣言情報と射影位置を使い、同名の別の宣言や別フィールドの制約を原因にしない。安全性のState・Heap・要約を更新する規則は既存のものを使い、診断の履歴は別に保持する。履歴の長さや追跡の成否を受理・拒否や最適化へ使わない。

宣言・共有・結び直しとCFGの合流を追跡し、各制約について短い説明経路を選ぶ。局所の結び直しは古い履歴を置き換え、制約がなくなった値から古い名前の経路を表示しない。既知の格納先では実際の解析用オブジェクトグラフを参照して、別名の格納先や入れ子のフィールド・enum payloadへ伝わる制約を追う。readonlyが参照への制約であることは維持し、同じ割り当てを指す全参照へrootの制約を付けることはしない。

通常の関数と静的な関数値は、引数の制約を仮に渡した診断用の再解析で、仮引数・局所別名・返却まで説明する。変更する呼び出しでは、readonlyが渡った引数を選び、その引数を経由した変更箇所を呼び出し先の本体でも探す。これは既存の効果要約で拒否した呼び出しの理由を説明するものであり、新しい契約判定ではない。外部実装は本体を推測せず、未知の効果として説明する。

`checked access`は引き続き検査した操作対象の説明とし、`readonly propagation path`へ伝播経路を追加する。不透明な返却、未追跡のヒープ共有、診断用の追跡で精密に再構成できない部分は`uncertain readonly propagation path`と理由を表示する。呼び出し先の効果が引数単位までしか分からず、readonlyの制約が集約の内側だけにある場合も、拒否する範囲は変えず`cannot prove readonly access is preserved`と表示する。別のメンバーへの更新をその制約への確定的な変更として示さない。

経路は静的解析上あり得る伝播の説明であり、実行済みの履歴ではない。表示する経路を16段、呼び出し先の追跡を16段、射影を16段・64候補へ制限し、省略や不明性を明示する。再解析の命令・状態の複製・オブジェクトグラフの探索は100万単位までとし、上限では既存の診断を残して追加追跡を省略する。再帰する呼び出しも追跡を打ち切り、変更の候補では別の到達可能な操作も探す。

回帰テストで別名・結び直し・分岐・ループ・シャドーイング、既知のヒープ格納と別名、入れ子のフィールド・enum、呼び出し先の局所別名と返却、複数の変更引数、捕捉・静的コールバック、不透明な外部処理・ヒープ拡大、長い経路・再帰を扱う。HIR/LIR/C++の各出力段階で診断が一致し、失敗時には出力を作らないことも確認する。

通常389件・最適化無効229件、Formatting・Clippy・MkDocs strictの検証が成功した。readonlyの既存12テストと新しい経路8テストは、最適化無効版でも実行している。直前の`51a6da0`でサニタイザー35件・公開ジャッジ51解答を検証した処理系と比較し、既存172例すべてが引き続きコンパイルでき、生成C++もバイト単位で一致した。ソース・処理系・共通の生成C++のハッシュは[対照記録](beta07-readonly-routes-control.json)に保存した。診断のみの変更なので、サニタイザーと公開ジャッジはこの段階では再実行していない。完成条件10項目の照合も冒頭へ整理し、追加の性能改善と完成に必要な診断・CIの残件を分けた。
