# 処理系とライブラリの境界

基本操作・コンテナ・アルゴリズムは、通常のRusk関数またはC++へ接続するextern宣言で記述します。コンパイラは、宣言を解決して検査し、共有と制御の意味を保ってコードを生成する基盤を担います。

## ライブラリで定義するもの

| 対象 | 定義方法 |
|---|---|
| 基本型・演算・入出力 | 通常の型・関数宣言。C++本体と必要な生成情報を付ける |
| Vec・Dict・Set、反復型、遅延状態 | ジェネリックexternの型・操作、要素と保持先の宣言 |
| 探索・集約・ソート | Rusk関数または型付き操作・コールバックを参照するextern |
| 構造体・タプル・捕捉環境・enumのコピーと代入 | フィールド・variantを列挙する標準の導出テンプレート |
| タプルの比較・入力・出力 | フィールドと型付きの操作参照を使う標準テンプレート |
| Optionの構築・取得・短絡演算との接続 | 通常のenum・関数と、検査済みのvariant操作情報 |
| C++ランタイムの組立て | `extern symbol`、相対資源ファイル、明示した依存関係 |

外部型のC++表現は`cpp_name`、必要な操作は型付き参照で宣言します。C++本体を使うことは許容し、特定の型名・関数名に対する本体生成や文字列置換を増やさない方針です。

## コンパイラに置くもの

| 基盤 | 残す理由 |
|---|---|
| 構文、評価順、短絡、スコープ、ジャンプ | 通常の関数では評価しない分岐や束縛先そのものを表せない |
| 名前・型・候補の解決と具体化 | ライブラリ全体が使う共通の言語規則 |
| 構造体・タプル・enum・クロージャの形状とレイアウト | 構築・フィールド取得・パターン検査に必要な言語の構造 |
| 導出テンプレートの構造列挙・型分岐 | 共通の形状情報から標準テンプレートを展開するため |
| HIR/LIR、初期化、効果・共有・脱出・readonlyの検査 | ライブラリをまたぐ意味の整合性と契約を検証するため |
| 共有ABI、Unit、呼び出しアダプタと前方宣言 | 論理型とC++表現を一貫して接続するため |
| 所有・借用・値保持と直接生成の選択 | 効果・寿命の証明に依存するため |

型が同じC++表現を持つことは、Ruskの型が同じであることを意味しません。型名やC++本文の見た目から効果を推測することもありません。

## 信頼と不透明さ

読込元が埋め込み標準であることを、表示用のファイル名と独立に保持します。表現、効果、保持先、導出、直接生成などの信頼情報は標準宣言だけが使えます。メタデータが存在するだけで契約が有効になるわけではありません。

標準の契約も、型付きで参照した操作・コールバックの効果を検査してから有効にします。未知のextern、循環した依存、追跡できない共有元を安全とは仮定しません。射影先の書き込み・保持は引数全体へ保守的に伝え、書き換え後の共有先が変わり得る場合は候補を広げます。

一般の構造体コピー、内部の一時値をC++だけで扱う集約やハッシュ操作などには、不透明なままの操作があります。これは未移行の専用本体生成を意味せず、C++本文を解析しないことによる契約検査の境界です。

## 変更時に守ること

新しい操作はまず通常の宣言と型付き参照で表現します。コンパイラ側の支援が必要なら、型・関数名の特例ではなく、共通の構文・構造・ABI・解析情報として必要な理由を示します。共有、コピー、左から右の評価、失敗位置、Unit、未知の効果を確認します。

厳密な記法と上限は[extern](extern.md)、各工程は[パイプライン](pipeline.md)、検証の入口は[テストの実行](verification.md)を参照してください。
