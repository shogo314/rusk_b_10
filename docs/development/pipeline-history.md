# CST・AST・HIR・LIRとC++生成

<!-- rusk-docs: history -->

!!! note "過去の開発記録"
    このページの計画・件数・パス・測定値は記録当時のものです。現在の構成は[開発ガイド](index.md)、対応範囲は[言語リファレンス](../reference/status.md)を参照してください。

β05では処理系を次の段階へ分けています。名前・型の検査中にC++の関数本体を組み立てる方式から、型付きHIR、基本ブロックを持つLIRを経由する方式へ移行しました。

```text
Ruskソース
  → CST（構文解析）
  → AST（構文の整理・include展開）
  → HIR（名前・型・オーバーロードの解決と具体化）
  → LIR（基本ブロック・分岐・ジャンプ・解放）
  → C++20
  → g++などによる実行ファイル化
```

β07ではLIRを構築・検証した後に、関数効果・戻り値の共有元を固定点まで解析し、noescapeと読み取り専用の契約を検査します。宣言した制限は`AnnotateBinding`・`AnnotateAccess`・`AnnotateEscape`として保持し、推論した効果とは区別します。返却位置に加えて、注釈のない束縛の名前と位置も`DescribeBinding`としてHIR/LIRに保持して診断へ使います。これは契約注釈や効果の根拠とは別の情報で、C++生成と保持場所の解析では無視します。検査後に要約をHIRへも反映し、両方のIRを検証してから出力します。現在は推論した効果を引数借用と閉じたBool・Int・Charの値保持へ利用します。これらのC++表現はバックエンドで選び、最適化の有無でHIR/LIRの解析情報を変えません。[実装と性能](beta07-performance.md)に条件を記録しています。[β07の実装状況](beta07.md)を参照してください。

追加した汎用enumとOption移行後の検証は[enumとOption移行](enums.md)に記録しています。以下の測定・件数は各段階時点の記録です。

## 各段階を確認する

```bash
cargo build --locked
# 元のファイルの構文木。include先は展開しない。
target/debug/rusk compile examples/beta05/control_flow.rusk --emit cst -o /tmp/control.cst
# includeを展開した利用プログラムのAST。
target/debug/rusk compile examples/beta05/control_flow.rusk --emit ast -o /tmp/control.ast
# 標準ライブラリの型・関数の宣言も含む、解決済みのプログラム。
target/debug/rusk compile examples/beta05/control_flow.rusk --emit hir -o /tmp/control.hir
target/debug/rusk compile examples/beta05/control_flow.rusk --emit lir -o /tmp/control.lir
# 通常の出力。--emit cppは省略可能。
target/debug/rusk compile examples/beta05/control_flow.rusk --emit cpp -o /tmp/control.cpp
g++ -std=c++20 -O2 /tmp/control.cpp -o /tmp/control
/tmp/control
```

出力先は `-o` で指定します。省略時は出力段階によらず `a.cpp` です。CSTとASTの出力は型検査の成功を保証しません。HIRとLIRは検査に成功した場合だけ出力します。既存の出力ファイルがある場合、失敗時にその古いファイルを削除する処理はありません。

ダンプは内部構造の確認用で、形式を固定した交換用ファイルではありません。HIR/LIRの `main` は末尾にあり、関数一覧には外部・標準関数のシグネチャも含みます。変数は `Local(n)`、仮引数は `Parameter(n)`、呼び出しは `function: n` で参照先を確認できます。

## コンパイル工程の実装

`compiler/mod.rs`の`Compiler::compile`は、宣言登録、本体の準備、HIR構築、LIRへの変換と解析、指定した形式の出力を順に呼び出します。宣言登録は`compiler/declarations.rs`にまとめ、型・ジェネリック宣言、enum、型情報の検査、具体関数・外部シンボルの順序を保ちます。

`compiler/pipeline.rs`は、未使用を含む関数本体とトップレベル文の検査、具体化によって増える本体・導出操作・native型の準備を完了させます。native契約の依存は不透明な状態から検証し、効果の固定点が確定してからnoescape・readonlyを検証します。HIR/LIRの整合性検査は、各解析の前後に行います。

関数・クロージャの検査中のスコープ、命令列、ループ、返却型・返却型推論、一時値、現在の関数は`compiler/context.rs`の`FunctionContext`へまとめます。入れ子の検査では、成功・エラーのどちらでも親の状態を復元します。型・関数の登録表と値・ループIDの採番は全体に保持し、子の検査後も登録や採番を巻き戻しません。クロージャの捕捉順序と生成物のキャッシュは従来の規則を保ちます。

関数IDごとのnative契約、依存と保存先の対応、lowering、enum操作、UnitのオブジェクトABIは`compiler/native_info.rs`の`NativeFunctionInfo`にまとめます。依存が未登録であることと、空の依存集合を登録した条件付き契約は区別します。前方宣言・各ABIの参照・効果問い合わせ・Unitブリッジの出力要求は、全体側の`NativeRequests`に保持します。メタデータが存在すること自体では標準の信頼権限を与えず、由来・契約検証・生成情報の従来の条件を使います。

ジェネリック関数は`compiler/generics.rs`で候補選択と具体化を分けます。従来どおり具体候補を優先し、明示した型引数を検査した後、読み取り専用の候補選択でテンプレートと束縛を確定します。具体化はキャッシュと上限を確認し、署名とキャッシュを先に登録してから本体・ABI・契約・loweringを展開します。この順序で再帰参照と前方参照を保ち、未選択の候補は具体化しません。

大きなモジュールの単体テストは対応する`tests.rs`・`namespace_tests.rs`・`retained_tests.rs`へ分け、元のモジュール名とテスト名を保ちます。fixtureの文字列は移動時の字下げで変更せず、`include_str!`の相対パスだけを新しい配置へ合わせます。

## CSTとAST

`rusk.par` から処理系のビルド時にParolのパーサーを生成し、`src/frontend/rusk_grammar.rs` が構文木を受け取ります。不要な句読点などは文法の指定で省かれるため、完全なソースの再出力を目的とした損失のないCSTではありません。

`src/frontend/ast.rs` は宣言・式・制御構文とソース位置を持つASTへ変換します。CSTでは二項演算を列として受け取り、優先順位・結合・比較の連鎖をAST構築時に確定します。`src/frontend/source.rs` がinclude先を解析してその位置へ展開し、重複・循環を検査します。

## HIR：解決済みのRusk

`src/compiler/mod.rs` と補助モジュールが、型・スコープ・初期化・関数の候補を検査し、`src/ir/hir/mod.rs` の型付き命令を作ります。

- 変数の参照先は元の名前ではなく、宣言ごとのID。仮引数IDは関数内、ローカルIDは処理系のカウンターから採番する。
- 関数呼び出しは一覧中のIDで、オーバーロードとジェネリック具体化の選択を完了済み。
- 型の表にはRuskの型名と構造体・タプルのフィールド、enumのvariantとpayload、配列・辞書・集合の要素型、クロージャの捕捉と呼び出し先などを保持する。
- `Object` は共有取得・フィールド取得・構築などを表し、`Rebind` は保持場所の結び直しを表す。
- コピー・オブジェクトの更新は、解決済みのcopy・更新関数の呼び出しとして区別する。
- `Scope`・`If`・`Loop`・`Break`・`Continue`・`Return` で制御構造を保持する。break/continueは対象ループのIDを持つ。
- `??`・比較の連鎖は、型検査を行いながら一時値と分岐へ展開する。

HIRの関数本体に、C++ソースや `std::shared_ptr` などのネイティブ型は含めません。`src/ir/hir/validate.rs` が定義済みの値・型、フィールド、呼び出しの引数・結果、分岐条件、脱出先などの整合性を検査します。

## LIR：基本ブロックとジャンプ

`src/ir/lir/mod.rs` はHIRの構造化された制御フローを基本ブロックへ落とします。各ブロックは単純な操作の列と、次のいずれか一つの終端命令を持ちます。

| 終端命令 | 動作 |
|---|---|
| `Jump` | 一つのブロックへ移る |
| `Branch` | Boolの条件に応じて二つの行き先から選ぶ |
| `Return` | 結果を返し、指定したローカルの共有を解放する |
| `Unreachable` | 到達しない経路。C++では異常終了として生成 |

if式は、結果用の保持場所を分岐の外に用意し、各分岐がそこへ共有を格納して合流します。ループは入口へ戻るジャンプ、breakは終了先、continueは次の反復の入口へのジャンプになります。SSAやphi命令は使わず、型付きの保持場所への代入で表します。

解放の整理では、各ブロックの入口に残り得る共有を前向きに解析します。合流点ではいずれかの経路で残る共有を保持し、確実に空の保持場所への重複した解放だけを取り除きます。到達しないブロックも削除します。この処理は最適化無効版にも共通です。

LIRの操作は構造化されたIf/Loop/Scopeや任意のソース文字列を格納できない別の型です。検査では保持場所、呼び出しのシグネチャ、条件、ジャンプ先、returnと解放対象を確認します。

## 共有の寿命とC++生成

各スコープに属する保持場所を追跡し、通常のスコープ終了とbreak/continueに必要な解放を挿入します。外側へジャンプする場合は、抜ける複数のスコープを内側から解放します。関数の仮引数の保持は呼び出し規約に従い、C++では引数オブジェクトが関数の終了時に解放されます。

C++では、基本ブロックをまたぐ保持場所を関数の入口で宣言します。一つのブロック内で定義・利用・解放まで完結する値は、ラベルに続く `{ ... }` 内で宣言します。gotoの行き先はその括弧の前なので、変数の初期化を飛び越えません。LIRの解放操作をその位置で出力し、入口へ移した変数の共有が不必要に残ることを防ぎます。

returnでは、返す値への共有を先に確保してから、ローカルの共有を解放します。返す文字がローカルの文字列を保持する場合も、返却後まで所有者が生存します。途中の共有を解放しても、別の変数やコンテナが保持したオブジェクトの中身を消すことはありません。

`src/backend/program.rs` がプログラムを組み立て、`src/backend/cpp.rs` がLIRをC++へ変換します。`src/compiler/cpp.rs` は標準コンテナ等のC++用ランタイム定義を渡す境界です。外部関数・標準ランタイムのネイティブ実装はHIR/LIR本体と別に持ちます。

## β03の高速化との関係

標準演算の直接生成は `src/backend/intrinsics.rs`、一時値は `lib/scalar.hpp`、入出力は `lib/io.hpp` を使い続けます。基本値の保持場所には最適化時だけ `RuskTemporary<T>` を選び、共有が必要になるまでヒープ確保を遅らせます。繰り返し実行する保持場所は、そのたびに新しい一時値へ置き換えます。

`--no-opt` はHIR/LIRを変えず、C++側の表現と標準演算の置き換えだけを変えます。専用テストで両モードのIRが一致することと、実際の確保削減・共有・診断を確認します。

## 今後の拡張

[ブロック式とラベル付き脱出](../reference/blocks-labels.md)を追加し、ブロック・結果用の保持場所・対象ループIDへ接続しています。値を返さず脱出する式は内部の制御フロー状態で区別し、継続する分岐だけで結果の型を決めます。HIRの検査前に脱出後の命令を除去します。一般のNever型、SSA、LLVM出力も未実装です。

LLVM向けには、このLIRからの命令生成に加え、共有の参照数管理・再帰的コピー・文字への借用・コンテナ・入出力・外部ABIの対応が必要です。現在のC++ランタイムをそのままLLVMの命令へ変換する仕組みではありません。

## 検証結果

2026年11月7日に、通常版222テスト・最適化無効版108テスト、ASan/UBSan/LeakSanitizerの12例、AOJ/Library Checkerの49解答805ケースが成功しました。AtCoder100問の公式サンプル279件も通常版に含みます。fmt・clippyとMkDocs strictも成功しています。

専用テストは `tests/pipeline.rs`、内部の整合性・解放の解析はHIR/LIRのモジュール内にあります。誤った関数シグネチャ・未定義の値・ジャンプ先を拒否し、外側のループへ抜ける際に内側の共有だけを解放すること、分岐の合流では残り得る共有を保つことを確認します。

最初の配置方法では、すべての一時値を入口に移した影響で長いコードのC++コンパイルが遅くなりました。重複した解放の除去とブロック内に完結する値の宣言配置を追加しています。未使用でもスコープ中に残すべき共有は除去せず、文字への共有による長さ変更の制限も維持します。

## 変更前のβ05との性能比較

WSL2 / Linux 6.6.87.2、AMD Ryzen AI 9 HX 370、GCC 15.2.0で、生成C++を `-std=c++20 -O2` にして測定しました。他のテストを終えてから実装を交互に実行し、7回の中央値を使い、全回の出力一致を検査しています。コンパイルは計測から除き、プロセス起動と入出力は含みます。

| 処理 | IR移行前のβ05 | HIR/LIR移行後 |
|---|---:|---:|
| 辞書の集計・走査 | 13.01 ms | 13.51 ms |
| タプル集合の登録・走査 | 21.07 ms | 20.67 ms |
| map/filter/fold | 87.86 ms | 87.35 ms |
| キー付き安定ソート | 25.13 ms | 24.16 ms |
| 整数入力と合計 | 29.03 ms | 29.32 ms |

この10項目では約−4〜＋4%で、大きな退行は見られません。単一環境・短時間の測定で、数%の差を有意な改善や悪化とは扱いません。共有オブジェクトやコールバックの既存の負担は残ります。
