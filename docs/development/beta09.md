## 文書コメント・ライブラリ検索・API文書生成

宣言とその説明をソースから取り出す共通基盤を検索とAPI文書生成に使います。組み込み標準ライブラリと利用者のライブラリに対応します。 [コマンドライン](../getting-started/cli.md#library-search)・[APIリファレンス](../library/api.md)

### 文書コメント

宣言の直前の行頭に連続して書く`///`を文書コメントとし、本文をMarkdownとして抽出します。通常の`//`コメントとは区別し、通常のコメントを自動的にAPIの説明にはしません。所属規則とファイル説明の`//!`は[文書コメント](doc-comments.md)に記載しています。

```text
/// 2つの整数の和を返します。
///
/// オーバーフローした場合は実行時エラーになります。
fn add(a: Int, b: Int) -> Int { return a + b; }
```

- 型・関数・extern宣言、構造体のフィールド、enumのvariantを抽出対象にする。
- 空行や通常のコメントで説明を切り離す。所定の位置にないコメントは説明として抽出せず、include先へも結び付けない。
- ファイル全体の説明には、コードより前の行頭に書く`//!`を使う。ファイル説明は名前空間を作らない。
- 概要・引数・戻り値・失敗条件・実例はMarkdownの本文や見出しで書き、専用タグは設けない。
- フォーマッタはコメントの内容と所属を保持し、コード例などのMarkdownを壊さない。

### 宣言情報と検索

構文解析した宣言から名前・種類・署名・型引数・引数注釈・説明・定義位置・ファイル情報を抽出します。ジェネリックは宣言単位で扱い、文書化のためにすべての型を具体化しません。C++本文を実行したり、C++をコンパイルしたりすることも前提にしません。

将来のVS Code拡張でも再利用できるよう、抽出処理をCLIの表示やMkDocs用の生成処理から分離し、宣言の位置と文書コメントの対応を保持します。エディタ連携のための不完全なコードの解析や言語サーバーの実装は今回の前提にしません。

- 型・フィールド・variantと、通常の関数・extern・オーバーロードを区別して列挙する。
- JSONなどの共通の機械可読形式を用意し、検索と文書生成で同じ情報を使う。
- 最初の検索範囲は名前・署名・説明の文字列検索とし、署名・概要・定義場所を表示する。検索対象・一致規則・CLI・結果の順序を決める。
- includeの重複、同名宣言、標準ライブラリと利用者コードの由来を扱い、同じ宣言の重複掲載や異なる宣言の混同を避ける。
- 型から呼び出し可能な関数を探す検索、参照箇所の検索、IDE連携は最初の範囲に含めない。

### API文書の生成と検証

抽出した宣言情報からAPIリファレンスを生成し、既存のMkDocsサイトへ組み込みます。導入・チュートリアル・共有や評価順序の説明は手書き文書として維持し、生成対象と編集元を明示します。標準ライブラリに説明コメントを整備し、追加する数値・走査・集計APIも掲載します。

生成順序とリンク・識別子を安定させ、ソースへのリンク、オーバーロード、文書コメントの所属、整形前後の抽出結果の一致、検索結果を検証します。掲載例のコードを検証する方法と実行対象の指定を決め、未検証の例を実行確認済みと扱わないようにします。生成とstrictビルドをCIへ組み込み、署名や説明の変更が文書へ反映されることを確認します。

## 全順序の比較とソート

`<=>`は型の標準の全順序を表します。実装フック`__cmp__`の戻り型は標準enumの`Ordering`です。Floatの部分比較と明示的な全順序比較は`partial_cmp`と`total_cmp`を使います。 [全順序](../reference/operators.md#total-order)

- `<=>`の比較は全順序の法則を満たし、`Equal`は通常の`==`と整合することを契約として要求する。利用者定義の実装について、法則を処理系が完全に証明することは前提にしない。
- Intなど全順序を提供する標準型に実装し、Floatには既定の`<=>`を用意しない。Floatの通常の大小比較はIEEE 754に沿ってNaNとの比較を偽とし、部分比較とNaNも含めた明示的な全順序比較を名前付き関数で提供する。後者の順序ではNaNと符号付きゼロの扱いも明記する。
- `<`・`<=`・`>`・`>=`の専用フックに適用可能な候補がなければ、同じ向きの引数で`<=>`を一度呼び、その結果から比較を補う。適用可能な専用フックがあれば優先する。
- 専用フックの候補が曖昧、返却型が不正、本体の検査が失敗する場合は診断する。`==`・`!=`はそれぞれのフックで定義する。
- 両オペランドを左から一度ずつ評価し、補った呼び出しにも通常の具体化・効果・共有・readonly/noescapeの解析を適用する。比較の連鎖での評価回数と短絡も維持する。
- タプルの全順序は要素すべてに`<=>`がある場合に辞書順で導出する。既存の配列・タプルなどの比較との整合、要素の操作が不足する場合の診断を確認する。

既定の`sort`は要素型の`<=>`を、`sort_by_key`はキー型の`<=>`を使います。必要な操作がない場合は通常のコンパイルエラーにします。既存の`sort_by_comp`はBoolを返す比較関数を受け取り、厳密弱順序を契約として要求します。いずれも安定ソートとします。

Floatのソートでは比較方法を明示します。NaNを含む順序を決める名前付き関数を比較関数付きソートで使えるようにし、ソート本体にFloat専用の分岐を追加しません。通常の`<`を比較関数に渡すだけでは、NaNを含む入力の順序の契約を満たさないことを文書化します。min/max系の集計も、既定で使う全順序と明示した比較方法の区別を揃えます。

検証には、専用フック優先・候補不在・曖昧さ・誤った署名・ジェネリック具体化・評価順序、Floatの通常比較と明示的な順序、タプルの導出、安定性、既存ソートとの互換性を含めます。フォーマッタとAPI文書生成も新しい演算子と関連宣言に対応させます。

## 走査と集計

[コンテナと走査の設計方針](https://github.com/shogo314/rusk_b_09/blob/main/design/collections.md)を出発点にします。

| 対象 | 作業と実装前に決めること |
|---|---|
| enumerate | 添字と要素を遅延して返す。開始値、添字のオーバーフロー、要素の共有を定める |
| zip | 対応する要素を遅延して返す。長さ不一致をエラーにする方針を基に、終端確認の順序、余分な消費、副作用、対応する列数を決める |
| 逆向き走査 | 配列・文字列・範囲など、対応する対象とAPIを決める。要素の共有、構造変更の検出、逆向きに走査できない入力の扱いを定める |
| sum | Vec<Int>専用の操作から一般の走査・加算可能な型へ広げる。初期値の省略条件、コピーせず加算する規則、空入力の結果、既存APIとの互換性を確認する |
| min/max/argmin/argmax | 一般の走査に対応させ、空ならNone、同値なら最初を選ぶ方針を具体化する。選んだ要素の共有と、走査先頭からの位置を保つ |

map/filter・途中まで消費した反復状態との合成、空入力、短絡、副作用の順序、コピーした走査状態、readonly/noescapeと寿命を確認します。既存のfold/scanのコピー規則は維持します。Floatを比較・集計する際のNaNの扱いも数値型の規則と揃えます。

反復規約をOptionを返すnextへ移すかどうかは別途判断します。走査APIを追加するだけで規約全体の変更を必須とはしません。

## externの作成者が保証する引数契約

利用者のexternにも、引数の`noescape`・`readonly`を作成者の保証として付けられるようにします。通常のRusk関数は本体の解析で契約を検証し、externは宣言した契約を呼び出し側の解析に使います。無注釈のexternは、引き続き未知の効果を持つものとして保守的に扱います。採用した宣言の規則は[externの引数契約](extern.md#extern-parameter-contracts)を参照してください。

- `noescape`の保持・返却に関する制限と、`readonly`の変更禁止の範囲は、通常のRusk関数の同じ注釈と揃える。両者を付けても純粋性・停止性・失敗しないことや、他の引数・外部状態を変更しないことまでは保証しない。
- 通常のexternとジェネリックextern、関数参照・コールバックを経由する呼び出しにも契約を伝える。返却値や保持先との共有について、注釈が保証しない関係は未知のままにする。
- 注釈の組み合わせと宣言の整合性を検査し、不正な宣言は位置付きの通常の診断にする。C++実装が宣言した契約を破った場合の責任はexternの作成者にあることと、処理系による検出を保証しないことを文書化する。
- 標準専用の`effects`・保持先・返却別名・直接生成などのメタデータとの役割を整理する。この変更だけで、既存の標準専用プロパティをすべて利用者へ開放しない。
- 現在のextern注釈の拒否テストを更新し、保証された操作の受理、保証されない操作の拒否、無注釈の場合、具体化・間接呼び出し・Rusk関数越しの契約伝播を検証する。契約を守る実装で、最適化あり・なしと寿命の確認も行う。

既存の未知の効果を、指定した引数の契約が保証する範囲だけ精密化します。内部エラー経路の監査では、正当な契約付き宣言と不正な宣言を両方対象にします。

## 内部エラーの報告とエラー経路の監査

利用者のコードや実行環境に起因する失敗は通常の診断として返し、処理系が保証すべき内部不変条件の違反は理由を添えてpanicにします。CLIの入口で`std::panic::set_hook`を設定し、内部エラーであること、処理系のバージョン、処理段階、panicの理由とRust側の発生位置を報告します。バックトレースの取得方法と終了時の扱いも定めます。panic後の処理続行や回復は前提にしません。

導入と併せて、以下を監査・修正します。

- CST・ASTから名前解決、具体化、解析、HIR/LIR変換、C++生成まで、各段階が前提とする不変条件と、その検査の所在を確認する。
- HIR/LIRなどの整合性検査が、型・値・参照・呼び出し・制御構造・寿命に関する不整合を検出できるか調べ、不足する検査を補う。
- 既存の`panic!`・`unreachable!`・`assert!`・`unwrap`・`expect`、添字アクセスなどを調べ、利用者の入力で到達できる失敗を通常の診断へ直す。
- 内部エラーを単なる利用者向けエラーとして返している経路も調べ、利用者の入力の検査と内部不変条件の検査を分離する。既存の`Result`を一律にpanicへ置き換えない。
- 不正な構文・型・ジェネリック・extern宣言、includeやC++資源の不備、ファイルI/O、資源上限などは、位置と理由を伴う適切な診断にする。利用者が渡す不正なextern宣言も内部panicの理由にしない。
- 検出した不整合の後に出力処理を続けず、失敗時の出力ファイルの扱いを明確にする。

検証では、不正なIRを意図的に構築して内部検査が失敗することと、不正な利用者コードがpanicせず診断されることを確認します。panic hookの出力は子プロセスで検証し、既存の拒否テストに加えて監査で見つかった経路の回帰テストを用意します。構文入力の変異・生成テストも使い、未検査の経路を探します。

監査結果には、確認した範囲、追加・修正した検査、残る制限を記録します。構造的な整合性検査ですべての誤変換を検出できるとは扱わず、実行結果・評価順序・共有のテストも維持します。
