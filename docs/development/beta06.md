## パターンの型検査と網羅性

CSTから共通のパターンASTを構築し、対象の型に対してvariant・フィールド・定数・束縛を解決する。orの各候補の束縛名と型を揃え、同じ候補内の重複束縛を拒否する。

網羅性と到達不能は、コンストラクターによるパターン行列の特殊化で調べる。enumの各variant、Bool、ASCII Char、タプル・構造体・Unitを有限のコンストラクターとして扱う。IntとStrは定数以外の値がある開いた領域として扱う。ガード付き行は後続の網羅性を満たす行として登録しない。入れ子の未処理例を構築し、診断に表示する。解析と展開の量には上限を設ける。

`tests/beta06.rs`では、enumとBoolの組み合わせ9値を独立に列挙し、256種類のarm集合について網羅性・到達不能の期待結果と照合する。

## HIRと制御フロー

パターンの検査は通常のフィールド・variant操作、基本値比較、構造化分岐へ下げる。照合前に全armの判定と共有先を準備し、ガードを順番に評価する。ガードはarmごとに一度だけコンパイルし、偽の場合の後続armを複製しない。orは最初の完全な一致で束縛先を確定する。

ガード実行後に元のenumのタグやフィールドを読み直さないため、ガードから共有値を更新しても安全に取り出せる。共有先の中身をコピーして凍結する方式ではない。

if letとwhile letは共通の条件表現と照合処理を使う。一致側に束縛用のスコープを作り、既存の分岐・ループの初期化解析、ラベル、脱出と解放へ接続する。必ず脱出するガードにより実行されない本体は型検査したうえで、HIRのUnreachableに下げる。LIRでは既存のUnreachable終端になる。

## クロージャの捕捉

パターンの単独の名前が束縛かvariantかは対象の型で決まる。このため、構文だけから捕捉名を列挙する方式を、型検査時の実際の変数解決で捕捉を決める方式に変えた。パターンで束縛済みなら外側を捕捉せず、variant名なら本体の同名の外側変数を通常どおり解決する。

捕捉フィールドの格納・コピー順は従来の名前順を維持し、参照解決時に使ったフィールド番号を確定後に対応付け直す。捕捉フィールドの取り出しは呼び出し本体の先頭へまとめ、どの分岐で最初に参照しても定義済みにする。入れ子のクロージャの捕捉も外側の必要な捕捉へ接続する。構造化分岐の初期化解析は、先頭で初期化される捕捉の存在を扱う。

## enumの共通レイアウト最適化

空のvariantと一つの共有payloadを持つvariantだけからなるenumは、共有ポインターのnull状態を空のタグとして使う。Option固有の最適化ではなく、利用者定義の同じ形のenumにも、variantの順序にかかわらず適用する。入れ子のOptionやUnit payloadでもタグを区別する。Ruskの有効な値は非nullの共有オブジェクトであることを前提とし、externの実装にも同じ契約を求める。

HIRのEnum・Variant・VariantTest・VariantFieldは共通のままで、C++バックエンドの構築・タグ・取り出しヘルパーがレイアウトを吸収する。他のenumは引き続きstd::variantを使う。外側の同一性、payloadの共有、copyフック、コピー順序、代入前のスナップショットは維持する。

## 検証

共通入口は`python3 tools/test.py`。β06のテストを通常版・最適化無効版に追加し、サニタイザーには新しいパターンの実行例と共有・文字参照・ループ脱出の例を追加した。AOJのITP1_3_Cの別解とITP1_8_Bを新構文で実装し、公開ケースでも検証する。最終結果は通常260テスト、最適化無効146テスト、ASan/UBSan/LeakSanitizerの17例、公開51解答810ケースで成功した。新しい文書の完全なプログラム例7件も変換・実行した。fmt、Clippy、MkDocsのstrictビルドも成功した。CIはpush後に同じ共通入口で実行する。

## 追加した最小・最大演算子

`<?`・`>?`は加減算と比較の間の優先順位で左結合し、`<?=`・`>?=`は他の代入と同じ右結合とする。ASTでは通常の二項演算と複合代入へ下げ、HIR/LIRに固有の演算命令を追加しない。複数文字の複合演算に対応するため、更新フック名の組み立ては末尾の`=`だけを除く方式にした。

標準の型引数付き`__min__`・`__max__`は選んだ値をcopyし、`__imin__`・`__imax__`は改善するときだけ既存の代入を呼ぶ。比較の結果をBoolとして検査する。具体的な型のフックで通常・更新をそれぞれ置き換えられ、既存のInt用min/max関数は維持する。

標準ライブラリーのRusk関数から行う呼び出しは、呼び出し元の位置を受け継ぐ情報をHIRのCallへ保持する。C++バックエンドはそれをABIの位置引数に下げ、最適化した演算でも同じ位置を使う。位置引数が存在しないmainからの不正な継承はHIR・LIRの検証で拒否する。同じフックの複数の使用箇所について、実行時エラーの行・列が実際の演算子位置になることをテストする。

`tests/minmax.rs`は優先順位と比較の連鎖、625組の整数の独立な期待値、両端値、共有とコピー、同値と更新不要時のpayload、添字と右辺の評価回数、オーバーロード、脱出、診断を検査する。サニタイザーに2例を追加し、AOJのDPL_1_AとALDS1_1_Dでも更新演算子を使う。利用者向けの文法と共有の規則は[最小・最大演算子](../reference/operators.md#minmax)を参照。

追加後の検証は通常270テスト・最適化無効156テスト・サニタイザー19例・公開51解答810ケースで成功した。最小・最大演算子の文書の3プログラム例も変換・実行した。既出の性能測定JSONはパターン機能を実装した時点の記録で、今回の演算子の個別性能を測ったものではない。

## 標準ライブラリへのアルゴリズム移行

配列の`find`を`lib/core.rusk`の`fn find<T>(a: Vec<T>, value: T) -> Option<Int>`へ移した。コンパイラの専用C++生成と`find`専用の引数型ヒントを削除し、通常のジェネリック関数の解決で処理する。走査には既存のイテレータを使い、比較直後にも有効性を検査する。一致したときの早期returnでも構造変更を検出する。整数の`min`・`max`・`abs`も、同じファイルの通常のRusk関数へ置き換えた。返す値の独立性と、absのオーバーフロー時に利用者の呼び出し位置を示す動作を維持する。

`sum`もRuskのforで実装して比較したが、100万要素の合計を20回求める試行では、生成C++を同じ`g++ -std=c++20 -O2`でビルドし、3回の実行の中央値が約48msから324msへ増えた。そのため、今回の移行では`sum`の既存のextern実装を維持した。これは単一環境の予備測定であり、一般的な性能保証ではない。走査の共有や参照カウントの最適化は別の課題とする。findも、10万要素の不一致探索を20回行う別の予備測定では、5回の中央値が約30msから87msへ増えた。専用C++から通常のRusk関数への移行は現時点では無コストではなく、この探索の速度差も今後の最適化対象となる。

回帰テストでは、findの先頭一致・不在・空配列、入れ子配列の型推論、明示型引数、ユーザー定義の等値比較と早期終了、比較中の構造変更、戻り値の独立性、実行時エラー位置を確認する。

移行後の確認はfmt・Clippy、通常274テスト、最適化無効160テスト、ASan/UBSan/LeakSanitizerの既存19例と追加1例、MkDocsのstrictビルドで成功した。公開ジャッジの全ケースはこの移行では再実行していない。

## 生成C++によるfind・sumの速度差の調査

移行前と移行後の生成C++を保存し、同じGCC 15.2.0の`-std=c++20 -O2`でコンパイルした。findは10万要素の不一致探索を20回、sumは100万要素の合計を20回行う。順番を交互に変えて7回ずつ実行し、中央値を採った。時間にはプロセス起動と配列の構築も含む。前節の予備測定と絶対時間は異なるが、倍率はほぼ同じだった。[入力・各回の時間・確保回数・環境](stdlib-codegen-benchmark.json)を記録している。

### 所有権コピーと局所変数の表現

生成コードでは、引数・変数の読み取りや宣言でも`Obj<T>`（shared_ptr）をコピーする。例えばRusk版sumのループ本体には、次の処理が含まれている。

```cpp
Obj<std::int64_t> rusk_v51=vector_123_21(rusk_v48,rusk_call_loc);
Obj<std::int64_t> rusk_v52=rusk_v51;
rusk_v51.reset();
Obj<std::int64_t> rusk_v53=rusk_v46; // totalへの一時的な共有
Obj<std::int64_t> rusk_v54=rusk_v52; // 要素への一時的な共有
```

イテレータ引数の値渡し、要素取得、ローカル束縛、totalと要素の式引数への共有で、計測用コードでは1要素あたり約5回の参照カウント増加が発生する。2000万要素を処理すると約1億回になる。旧sumはC++の整数ローカルへ加算し、要素は`const auto&`で参照しているため、反復ごとの所有権コピーがない。

findは、イテレータ・対象値・要素・比較結果・添字を保持する一時共有が重なり、同じ計測で1要素あたり約11回だった。旧findは要素の保持と等値比較の値渡しで約3回だった。

また、findの`let matched: Bool := current == value;`は、比較結果の一時値を`Obj<bool>`へ保存する。

```cpp
RuskTemporary<bool> rusk_v83=RuskTemporary<bool>((*rusk_v81 == *rusk_v82));
rusk_v84=rusk_v83; // rusk_v84はObj<bool>。ここで共有オブジェクト化する
```

`RuskTemporary`はスタック上の値として始まるが、Objへの変換でmake_sharedを呼ぶ。現状のC++生成はリテラル・一部の呼び出し結果をスカラー化する一方、宣言・共有を通じた非脱出スカラーの追跡は行っていない。

ただし、**旧findも等値比較の結果のBoolを毎回確保している**。両者の確保回数は、配列構築を含め約210万回でほぼ同じだった。移行後に確保回数が反復数ぶん増えたことが原因ではない。sumも両者とも約100万回で、ほぼ配列構築時の確保だった。Rusk版sumが反復ごとに整数を新規確保しているわけではない。

### 実験用C++での切り分け

| 処理 | 変更 | 中央値 |
|---|---|---:|
| find | 旧専用C++ | 21.8ms |
| find | 現在のRuskからの生成コード | 63.5ms |
| find | 局所Boolをインライン値で保持 | 48.1ms |
| find | 一時共有を借用へ置換 | 37.1ms |
| find | 上記の両方 | 21.9ms |
| find | 変更検査だけを省く | 63.4ms |
| sum | 旧専用C++ | 47.5ms |
| sum | Rusk版の生成コード | 323.6ms |
| sum | total・要素の一時共有とイテレータ引数を借用へ置換 | 198.4ms |
| sum | さらに配列要素自体を借用で取得 | 59.9ms |
| sum | 変更検査だけを省く | 320.7ms |

メモリ確保はoperator new、参照カウント増加はlibstdc++の`_M_add_ref_copy`へ計測を挿入して数えた。計測挿入が最適化へ影響し得るため、実行時間はこれらを挿入しない別の実行ファイルで測っている。

この入力では、構造変更検査の削除はほぼ効かず、所有権コピーの削減が大きく効いた。findでは局所Boolの確保も削減余地がある。gotoを含む基本ブロック構造を保った実験でも速度が戻るため、その構造だけで大きな差を説明するものではない。

借用や検査削除は実験用C++だけの変更で、コンパイラ本体には適用していない。特にユーザー定義の比較が配列を変更し得るfindでは、要素の寿命保持と変更検査を守る必要がある。最適化する際は、非脱出スカラーの追跡、一時参照の借用、コールバックのないInt走査での所有権コピー削減を一般的なIR解析として扱う。現時点のsumは引き続き既存のextern実装を維持する。
