# 将来の方針と未決定事項

ここに挙げる機能は、現在の処理系で使えるとは限りません。[対応機能と制限](reference/status.md)が実装状況の入口です。以下は開発順序や次版の完成条件を確定する計画ではありません。

## 維持する基本方針

競技プログラミングでの書きやすさと実行速度を重視します。共有・コピー・更新・結び直しを区別し、評価順序と実行時エラーの意味を保ったうえで高速化します。

基本操作やコンテナの実装は、Rusk関数とC++へ接続するextern宣言で記述します。コンパイラには構文、名前と型の解決、共有・効果・寿命の検査、ABI、構造を展開する共通基盤を置きます。任意のC++本文を安全とみなす推測は行わず、未知の効果は保守的に扱います。

## 未実装だが方向性があるもの

| 分野 | 方針 | 実装前に詰めること |
|---|---|---|
| 数値 | 任意精度整数を用意し、型間の変換を明示する | 整数リテラルの文脈型付け、対応する演算の範囲 |
| 整数演算 | 剰余累乗などの用途別の整数操作を検討する | 型、境界値、失敗条件 |
| 走査 | 反復規約と、変換先を指定する走査APIを検討する | 既存の走査との互換性、コピーと共有 |
| 配列 | 固定長の共有ビューとしてのスライスと、要素を直接格納する配列を検討する | 共有が生きている範囲、構造変更の禁止、readonlyの伝播、型と構文 |
| 辞書・集合 | キー順に走査できる整列コンテナを用意する | 比較の指定方法、計算量とAPIの保証 |
| 引数 | 名前付き専用引数と既定値を設ける | 構文、オーバーロードとの関係、既定値の捕捉と評価時点 |
| 型 | 再帰的な型、明示指定による比較・ハッシュ導出を扱う | 寿命、コピー・比較の停止性、導出の指定方法 |
| 読み取り制限 | 外側のコンテナと要素の権限を区別して表現する | 入れ子の型表記、返却値の権限、外側を共有したまま権限だけ変える操作の制限 |
| コンパイル時評価 | 通常の関数やループで定数表などを作れるようにする | 値引数の構文、副作用、評価できる操作、資源上限 |

既存の`fold`は初期値をコピーし、`sum`は初期値をそのまま最初の加算に渡します。新しい集計APIでも初期値と結果の共有を明記します。

## エディタとの連携

将来はVS Code拡張を用意し、構文の色分け、フォーマット、診断の表示、補完、ホバーでの型・署名・説明の表示、定義への移動を段階的に整えたいと考えています。実装時期と初版の対応範囲は未定です。

フォーマッタ、文書コメント、ライブラリ検索とAPI文書生成のための宣言情報を、エディタ連携でも再利用できる形に整えます。LSPを使う構成を候補とし、編集中の不完全なコード、未保存の内容、応答時間、位置情報の扱いは拡張の実装時に設計します。API文書用の宣言一覧だけで、型に基づく補完や定義の解決まで実現できるとは扱いません。

## 関数・名前探索の基盤と今後の拡張

ジェネリック関数の名前探索は、定義場所での通常探索に、直接の実引数型の定義スコープからの候補を加えます。ローカルなstruct・enum、ジェネリックを含むローカル関数の捕捉に対応しています。内側の同名候補が外側を隠し、適合候補のうちジェネリックな引数が少ないものを優先します。捕捉付きの関連操作も、必要な環境を取得できる場所からRuskのジェネリック関数やexternの型付き参照を通して呼べます。[仕様](https://github.com/shogo314/rusk_b_10/blob/main/design/local-functions.md)と[作業計画](development/plan.md)を参照してください。

オーバーロード集合・未具体化ジェネリック関数の静的な受け渡しにも対応しています。参照した場所の候補と名前を保持し、呼び出し時に引数型からの候補を加えて選び、必要な捕捉環境を関数値が保持する仕様です。

これらの使い方と制限は[関数](reference/functions.md)と[関数の受け渡しと捕捉](reference/closures.md)を参照してください。名前付き・既定引数や動的な共通関数型は、この基盤とは別の拡張として検討します。

## 採用を決めていない案

無名関数の引数型省略、`_ + 1`のようなプレースホルダー、名前付き関数の式本体、要素ごとのドット演算は候補です。提案例を現在使える構文として扱わないでください。

再帰的な型を扱うことと、オブジェクト同士の循環共有を認めることは別の判断です。循環共有の可否・解放・コピー・ハッシュは保留しています。

## 初期の完成条件と分けて考えるもの

LLVMバックエンド、Unicode専用型、動的に型消去した共通の関数型は、現在の基本機能を整えるための前提ではありません。とくに関数の受け渡しは静的な具体化を基本とし、動的な共通関数型は当面の対象に含めていません。

for文の和を多項式に置き換えるような高度な最適化は、現在の作業対象ではありません。基本操作・共有・ABIの共通化と、生成コードの検証を優先します。

## 継続して整えること

言語機能とともに、診断、テスト、examplesと文書例の検証、測定条件を揃えた性能比較を整えます。サンプル一致や特定のベンチマークだけで、言語全体の完成や速度目標の達成とは判断しません。
